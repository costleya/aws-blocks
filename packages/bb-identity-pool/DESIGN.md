# IdentityPool design

IdentityPool provisions an `AWS::Cognito::IdentityPool` with unauthenticated identities enabled and the classic flow disabled. It always attaches an unauthenticated guest role, which starts with no application permissions. When configured with an existing IAM OIDC provider, it also attaches an authenticated role. Each role trust policy requires the provisioned pool audience and its corresponding Cognito authentication-method reference (`unauthenticated` or `authenticated`).

IdentityPool registers itself as a runtime identity provider. A `LambdaCompute` associates the pool's structural `{ fullId }` reference with its resource grants at synthesis. It does not assume an identity during dispatch. Application methods explicitly call `await identityPool.assumeForIdentity(context)` before user-scoped BB operations; operations without an assumption use the ordinary Lambda execution-role client. IdentityPool itself does not add application permissions to either pool role; resources grant authenticated or guest access explicitly.

At runtime `assumeForIdentity()` branches before any Cognito call. An absent authorization header uses Cognito's unsigned guest enhanced flow: `GetId` and `GetCredentialsForIdentity` without `Logins`. A valid bearer token uses the authenticated enhanced flow: `GetId` with the fixed pool and fixed `Logins` map, then `GetCredentialsForIdentity` with the same map. A supplied malformed or invalid authorization header is rejected and never retried as a guest flow. The second response's Identity ID is canonical because Cognito may merge identities during the exchange. The method exposes only the identity ID and authentication state through its result and `BlocksContext.identity`; the raw credential set remains request-local in Core's async identity context. A failed attempt clears any previous selection and poisons the request against a fallback, and request completion invalidates the scope, including deferred iterators. The separate `run()` callback API still scopes a callback when explicitly called.

The local mock accepts only configured token-to-identity mappings for authenticated requests. It creates a fresh, nonpersistent guest identity for each request without an authorization header; it makes no persistence, upgrade, or guest-identity reuse promise. Unknown, malformed, oversized, inherited, and invalid supplied tokens fail with `IdentityPool.Unauthorized`; unavailable configuration or Cognito responses that cannot yield usable temporary credentials fail with the sanitized `IdentityPool.Unavailable` error.
